# ltcode 实现说明

记录几个**容易算错**的地方。每一条都对应一个真实 bug、一次真实的错误计算，
或一个必须写在纸面上的设计取舍。

## 1. PLAN 里的 R ≈ 21.7 是 δ=1.0 的数

PLAN §4.1 写：

> **测试锚点**：K=1000 / c=0.1 / δ=0.5 时 `R ≈ 21.7`

这个数字与它自己给的公式不符。`R = c·ln(K/δ)·sqrt(K)`：

```
δ = 1.0 :  0.1 × ln(1000)  × sqrt(1000) = 0.1 × 6.907755 × 31.622777 = 21.844
δ = 0.5 :  0.1 × ln(2000)  × sqrt(1000) = 0.1 × 7.600902 × 31.622777 = 24.036
```

**21.7 属于 δ=1.0**。PLAN 在同一个句子里既指定了 δ=0.5、又给了 δ=1.0 的 R。

处理方式：实现取 PLAN 明确指定的 **δ=0.5**（即 24.036），并且测试**同时
锁定两个值**（`21.844` 与 `24.036`，各带容差断言），这样以后无论谁想
"按 21.7 去改实现"都会撞上一条明确的测试。README / API.md 都写明了这件事。

不选另一条路（按 21.7 反推 δ）的理由：δ 是**调用方要给的参数**（目标失败
概率），不是从 R 反推出来的量。让参数服从一个手算的近似值，是本末倒置。

## 2. 用拒绝采样，而且**不靠统计测试验证它**

`next_below(n)` 用拒绝采样而不是裸取模。裸取模的偏差量级：

```
偏差 = (2^64 mod n) / 2^64
n = 7 :  2 / 2^64 ≈ 1.08e-19
```

**这个量级在任何统计测试里都不可能被观察到** —— 你需要 10^18 次抽样才能
看到一个多出来的计数。所以"跑 70000 次看频率"这类测试**并不能**证明
拒绝采样是对的；它只能证明"实现没有明显坏掉"（比如把 n 写错、或者用低位
掩码）。

因此真正锁定行为的是这一条（`rng_test.mbt`）：

```moonbit
test "prng rejection threshold is exactly 2^64 mod n" {
  inspect(rejection_threshold(7), content="2")    // 2^64 ≡ 2 (mod 7)
  inspect(rejection_threshold(13), content="3")
  inspect(rejection_threshold(3), content="1")
  inspect(rejection_threshold(10), content="6")
  inspect(rejection_threshold(8), content="0")    // 2 的幂 → 永不拒绝
  ...
}
```

`2^64 mod 7 = 2` 是可以手算的（`2^3 ≡ 1 mod 7`，`64 = 3·21+1`，故 `2^64 ≡ 2`）。
把判定逻辑拆成 `rejection_threshold` + `map_below` 两个纯函数，是为了让
"哪些原始值必须被丢"成为一个**可直接断言的命题**，而不是一个需要统计
推断的命题。

还有一条测试证明"如果裸取模，偏差在小范围内是可见的"：在 `[0, 2^24)` 上
`n = 7`，`2^24 mod 7 = 1`，裸取模下余数 0 比余数 2 多 1 个计数。这证明了
偏差**真实存在**，只是在本项目的实际抽样量下不可见。

## 3. 我一度把测试写成"断言运气"

`decoder_test.mbt` 最初的版本有一条：

```moonbit
test "decoder: ample overhead always completes for many seeds and K" {
  for k in [1, 2, 3, 5, 10, 17, 40, 64] {
    ... 3.0 overhead ...  assert_true(r.is_complete())
  }
}
```

它在 K=10 上失败了。查下去发现：那条 seed 下 30 个符号里**一个度为 1 的
都没有**，`resolved == 0`，剥皮根本无法启动。

这不是 bug。K=10 时 μ(1) ≈ 0.1466，30 个符号全不为 1 的概率是

```
(1 - 0.1466)^30 ≈ 0.0086   ≈ 0.86%
```

实测 20 条种子里出现 1 条（`s=17`），与理论一致。

**这条测试错在它断言了一个 LT 不保证的东西。** 正确写法是两条：

1. 成功率断言 —— 阈值取**实测**值向下取整（不是"必须 100%"）：
   ```
   K=10 oh=3.0 → 实测 196/200 → 阈值 0.95
   K=10 oh=2.0 → 实测 175/200 → 阈值 0.80
   K=17 oh=2.0 → 实测 183/200 → 阈值 0.85
   K=40 oh=2.0 → 实测 194/200 → 阈值 0.92
   K=64 oh=2.0 → 实测 196/200 → 阈值 0.93
   ```
2. 结构性断言 —— 遍历种子找到一条"整组无度 1"的，断言 `resolved == 0`
   且 `missing` 是全部下标。**不硬编码某个具体 seed**（seed 派生细节
   可能在修 bug 时合法地改变），而是遍历找到满足前提的那一条。

第 2 条是关键：它把"失败"从一个黑箱变成一个**有解释的**结果。

## 4. 诚实性：两个视图必须一致

`Incomplete(recovered, missing)` 携带两个视图。它们信息等价，所以很容易
实现成两段独立的计算 —— 然后某天其中一段漏了一个边界情况，两个视图
就开始互相矛盾。

现在的实现方式：`resolved` 是唯一的真相（`Array[Bytes?]`，`None` = 未解出），
`missing` 从它**派生**：

```moonbit
let missing : Array[Int] = []
for i = 0; i < k; i = i + 1 {
  if resolved[i] is None { missing.push(i) }
}
```

并且有测试直接断言两个视图一致：

```moonbit
let none_positions : Array[Int] = []
for i = 0; i < recovered.length(); i = i + 1 {
  if recovered[i] is None { none_positions.push(i) }
}
assert_eq(none_positions, missing)
```

**绝不填零**这条由另一条测试守：跨 200 条种子，凡是报告 `Incomplete`，
每一个 `Some(v)` 都必须逐字节等于真实源符号。

```moonbit
match recovered[i] {
  Some(v) => if v != block.sources[i] { lies = lies + 1 }
  None => ()
}
```

`lies == 0` 是断言。如果实现补了零字节，这一条会立刻失败。

## 5. 真实缺陷：`splitmix64(seed ^ index)` 让试验不独立

这是本项目最严重的一个 bug，也是最难发现的一个 —— **因为它让数字变好看了**。

### 现象

K=1000、overhead=1.17、每 200 次试验算一块，跑 10 块：

```
consecutive-seed block rates: [0.585, 1, 0.565, 0.175, 0.71, 0.285, 0, 0.115, 0.015, 0]
```

块间标准差 **0.350**。而 n=200、p≈0.345 的二项分布只允许

```
sqrt(0.345 × 0.655 / 200) ≈ 0.0336
```

**差了 10 倍**。一块 200/200 全中，另一块 0/200 全灭 —— 这不是抽样噪声，
是相邻种子的试验**高度相关**。

当时测出的 overhead=1.2 成功率是 **1.000**（100/100 全中），后来修完
重测是 **0.810**。也就是说那个漂亮的 1.000 **完全是假象**。

### 根因

旧实现：

```moonbit
pub fn symbol_rng(seed : UInt64, index : Int) -> Ltrng {
  Ltrng::new(splitmix64(seed ^ index.to_uint64()))   // ← 错
}
```

`seed ^ index` 在"seed 固定、index 递增"时只翻转低位；在"index 固定、
seed 递增"时同样只翻转低位。`splitmix64` 会扩散这些位，但**扩散后的第一个
输出**在相邻输入上落进 CDF 的**同一段区间** —— 而第一个输出正好被用来
抽度数。结果是相邻种子的整批符号度数分布几乎相同。

### 修法

```moonbit
pub fn symbol_rng(seed : UInt64, index : Int) -> Ltrng {
  let mixed = splitmix64(
    splitmix64(seed) ^ splitmix64(index.to_uint64() + 0x9E3779B97F4A7C15UL),
  )
  Ltrng::new(mixed)
}
```

`seed` 与 `index` **各自**过一遍 splitmix64（各自扩散到全 64 位），再异或，
最后再过一遍。相邻 seed 或相邻 index 都会让派生状态彻底不同。

### 修完的验证

```
consecutive-seed block rates: [0.515, 0.525, 0.475, 0.465, 0.465,
                               0.515, 0.445, 0.52, 0.49, 0.465]
A mean/sd = 0.488 / 0.0288        ← 与二项噪声 0.0336 相符
```

恢复到二项噪声量级。

### 为什么这件事值得写下来

它是**"测试通过"不等于"结论正确"**的教科书例子。当时所有测试都是绿的：
确定性测试通过（同参数两次相同）、无放回测试通过、分布测试通过、
端到端往返通过。Measured success rate 甚至比现在更"漂亮"。

坏掉的只有一件事：**那些数字不是独立抽样得到的**。而这种坏法只能通过
"检查试验之间是否独立"来发现 —— 它需要主动去看块间方差，不是被动等
测试报红。

这也是为什么现在 `metrics` 的注释里写：「不使用墙钟时间，且成功率是
二项分布意义下的成功率」，以及为什么 README 里给了**两个种子基准**的
对照表。

## 5b. 真实缺陷：剥皮会在损坏的数据上报"成功"

这是比第 5 节更危险的一个 —— 因为第 5 节的 bug 只是让**数字**失真，
这一个会让**输出**是错的。

### 现象

K=20、overhead=2.0，把收到的符号里**一个度为 1 的符号**的第一个字节
翻转（`^ 0xFF`，模拟传输错误）：

```
complete=true   inconsistent=0
WRONG source symbols after tampering: 7 / 20
```

解码报 `Complete`，调用方会写出一个 4000 字节的文件，内容有 35% 是错的。

### 为什么 `inconsistent` 计数器没抓住它

我原本以为 `DecodeStats.inconsistent` 能兜住这种情况。它抓不住，原因
在算法结构里：

`inconsistent` 只在下面这条路径上才会自增：

```
某个符号降到度 1 → 它要求的源符号 s 已经被别的符号解出 → 比对两者的值 → 不同则 +1
```

而一个**本身就是度 1** 的符号，它的累积值**就是**那个源符号 —— 没有第二个
独立来源可以与它比对。它第一个被解出，之后所有包含 s 的符号都用它的值
去消元，错误就这样传播到整个下游。

方程组在这个意义上是**自洽的**：所有方程都被满足，只是满足的是"错误
但一致"的解。这不是实现 bug，是 LT 的数学性质（没有校验方程）。

### 修法

不能靠解码器自己发现，必须**从原始数据带一个校验和**：

- 容器 v2 在头部加 `payload_hash`（FNV-1a 64，8 字节）
- `pack_container` 收的是**原始 payload 字节**（不再是 `payload_len`），
  自己算长度与哈希
- `cmd_decode` 在写文件**之前**重算 `payload_hash(bytes)` 并比对，
  不一致就 `exit 3` 且**不写文件**

实测（CLI 层，翻转 payload.ltc 第 32 个符号的首字节）：

```
ltcode: decoded payload FAILED checksum: got 0x354f7a617b24837d,
                                            expected 0x408f149e6f4ea445
  the decoded bytes were NOT written to disk
exit=3
```

### 一个反直觉的细节：不是每次篡改都该失败

同一份 `payload.ltc`，翻转**第 60 个字节**（属于一个度 > 1 的符号）：

```
decoded OK: K=100 symbols=300 payload=4000 bytes (checksum verified)
exit=0
```

这是**正确**的，不是校验和失灵。LT 有冗余：一个度 > 1 的符号被改坏，
它变成方程组里的一条"错误方程"，但只要剩余方程仍然足够，剥皮会解出
**正确**的全部源符号。错误方程被孤立掉，没有污染任何东西（实测
`WRONG = 0 / 20` 的那个用例就是这个情形）。

所以判断标准不是"数据被改过吗"，而是"解出来的东西对不对" —— 后者由
校验和回答。这也说明为什么校验和必须来自**原始 payload**，而不是
"收到的符号是否一致"。

### 版本号因此变成 2

旧格式（v1，无校验和）不能被静默接受 —— 那等于把"无法验证"的容器
当成合法的。所以魔数从 `"LTC1"` 变成 `"LTC2"`，`unpack_container` 遇到
v1 直接报错。宁可让旧文件明确不被接受，也不要让它悄悄降级成"无验证"。

### 这个哈希的能力边界

FNV-1a 64 抓的是**意外损坏**：改字节、截断、拼接错误、把两批符号混在
一起。它**不抗主动构造**（有人可以故意造一个哈希相同的 payload）。

本项目的声明就到这里，README 里也写明了。要防水篡改应该换成
SHA-256 或带密钥的 MAC —— 那是另一个安全目标，不是纠删码的职责。

## 6. 复杂度用操作计数，不用墙钟

PLAN §6 要求"断言解码时间随 K 近线性（用操作计数而非墙钟时间）"。

`DecodeStats` 记录：

```moonbit
received : Int      // 收到的符号数
subset_slots : Int  // Σ degree（建表的关联总数）
resolved : Int      // 解出的源符号数
xor_bytes : Int     // 累计 XOR 字节数 ← 复杂度主项
inconsistent : Int  // 输入自相矛盾时为非 0
```

测试比较 K=200 与 K=400（同 overhead=2.0）：

```moonbit
let slots_ratio = big.0.to_double() / small.0.to_double()
let xor_ratio = big.1.to_double() / small.1.to_double()
assert_true(slots_ratio < 2.6)   // 线性 ≈ 2，平方 ≈ 4
assert_true(xor_ratio < 2.6)
```

阈值 2.6 而不是 2.0：K 翻倍时平均度数会缓慢漂移，比值略高于 2 是正常的；
但平方实现会给出 ≈ 4，2.6 足以区分"线性"与"平方"。

墙钟时间在 CI 上不稳，而且**无法区分**"渐进复杂度错了"与"常数因子大了"。
操作计数可以。

## 7. 解码器的反向索引用 CSR

第一版用 `Array[Array[Int]]`（每个源符号挂一个"包含它的符号"列表）。
对 K=1000、1200 个符号（平均度数 10）那就是 1000 个 `Array` 对象，
每个要单独分配 —— 分配次数随 K 线性增长，常数很大。

现在用 CSR（compressed sparse row）：

```
counts[s]   = 源符号 s 被多少个收到符号包含
offsets[s]  = counts 的前缀和（每个源的槽位起点）
rev[...]    = 展平后的反向索引
```

两次线性扫描建好，之后 `for idx in offsets[s] .. offsets[s]+counts[s]`
直接遍历。整块内存只有 2 个 `FixedArray[Int]`。

这一条没有单独测试（它是纯性能改动，行为不变），但 `decode_with_stats`
的 `subset_slots` 能间接看出结构正确 —— 它等于所有子集长度之和，
而 CSR 的 `fill[s]` 累计必须与 `counts[s]` 一致，否则会越界（wasm 下会
直接 trap）。

## 8. 补零发生在切块，不在解码

`SourceBlock::from_bytes(data, k)` 把数据切成 K 段；最后一段不足时**补零**。
这在 COBOL 项目里是禁忌（会掩盖缺失），在 LT 里则是必要的，因为编码要求
所有源符号**等长**。

区分点在于：补零的信息**没有被丢掉** —— `payload_len` 记录了原始字节数，
`reassemble` 按它截回。所以：

- 补零 = "末尾对齐用的填充"，可逆，且长度记录在文件头
- 解码填假数据 = "假装解出了缺的符号"，不可逆，且会让调用方拿到错数据

前者是编码器的事，后者被严格禁止（见第 4 节）。

有一条测试往返验证：4000 字节 → K=100 → symbol_len=40（正好整除，
所以这次没补零）→ 解码 → SHA-256 相同。非整除的情况由
`container_test.mbt` 的 `payload_len: 13` 那条覆盖。

## 9. 参数量化：编解码两端必须过同一个函数

容器头把 `c` 与 `delta` 存成**百分之一的整数**（`round(x*100)`）：

```
c = 0.1   →  10
δ = 0.5   →  50
```

为什么必须量化而不是存 IEEE 754 双精度原样（8 字节 × 2）：是为了让
文件头长度固定、可比对（有测试逐字节锁定偏移）。但代价是**精度损失**。

关键点：这不是"损失的精度可以忽略"，而是**两端必须算出同样的值**。
`c`/`δ` 决定子集抽样，如果编码端用内存里的 `0.1`、解码端用文件里的
`dequantize(10)`，只要两个浮点数不逐位相同，某些边界的抽样就会分出
不同的度数 —— 然后解码失败得莫名其妙。

因此实现里两个方向都过同一对函数（`quantize_param` / `dequantize_param`），
并且测试断言 `quantize(dequantize(q)) == q` 对全部 q ∈ [0, 100] 成立。
`0.1` 与 `10/100` 在双精度下是同一个值（因为 `10/100` 就是精确的除法
再舍入），但这条测试保证的是**函数互逆**，不是"某个巧合"。

## 10. 不能说"1.2 开销就 100% 成功"

README 里的曲线是实测的，1.2 处是 **0.793 ~ 0.808**，不是 100%。

这一点必须显式写在文档里，因为文献里经常说"LT 在 1.2~1.3 开销下可靠"。
那个说法通常指的是**加上了 inactivation 的实现**（或者 K 足够大、
c/δ 调过参）。本项目的 v1 是**纯剥皮**，1.2 处就是有约 20% 的失败率。

剥皮为什么会卡住：解码过程中每一步都要求"存在一个度为 1 的未解出符号"。
当剩余符号的度数分布已经不含 1（所有剩余符号都覆盖 ≥ 2 个未解出的源），
循环就停在原地。这不是 bug，是 O(K) 复杂度换来的固有性质 —— 也正是
inactivation 存在的理由。

**正因为如此，`Incomplete` 的 `missing` 才有价值**：调用方看到"还差 17 个"，
再要 20 个符号重解一次，比"整体失败，重来"好得多。本项目的设计把
这件事做成了可用的接口，而不是把失败藏起来。

## 11. 验证方法与结果

**GF(256)** —— 两张表由不同原理产生：

- `gf256_mul`：由生成元 3 的连续幂构造 exp/log 表（假设 3 是本原元）
- `gf256_mul_peasant`：俄罗斯农民乘法，只做移位与条件 XOR（假设约化多项式 0x11B）

全部 65536 对逐项相等 → 两个假设同时成立。这是真正的交叉验证，
不是"同一份逻辑跑两遍"。

**度数分布** —— 归一化容差 1e-12 在 9 组 `(K, c, δ)` 上断言
（含 K=1/2/3 边界、K=5000/c=0.03）。P(d=1) 用 10000 次采样对比 3σ
（σ = sqrt(n·p·(1-p)) ≈ 14.3，3σ ≈ 43）。

K=20 下还做了**整条 pmf** 的核对（200000 次采样，每个桶的相对偏差 < 25%）——
只测 d=1 一个点会漏掉"其余度数全错"的实现。

**编码器均匀性** —— K=6、d=3 时全部 `C(6,3) = 20` 个三元素子集，
200000 次抽样，每个子集 ~10000 次，最大相对偏差 < 5%。这能抓住
"Floyd 写错导致某些子集永不出现"（那会让某些桶为 0）。

**端到端** —— 4000 字节实测往返 SHA-256 相同；数据不足时 `missing`
是真实下标（51 个，逐条列出）；退出码用 native 二进制核对 0/1/2/3。

## 12. 已知未覆盖的地方

诚实列出：

1. **wasm 与 native 的逐字节一致性没有实测**。设计上排除了宿主随机源
   （无时钟、无地址、无哈希随机化），但"跑一遍比对"这件事没做。
   `moon build --target wasm` 成功，但没把 wasm 输出与 native 输出
   做 diff。
2. **1.19 以上的成功率只测到 500~1000 trials**，所以"1.19 以上接近 1.0"
   这个说法带 ±1.5% 量级的抽样误差。要更紧的置信区间需要更大样本。
3. **大 K 没有压测**。K 上限是 `1 << 20`，但测试只到 K=1000
   （加上一条 K=1<<20 的"不分配 O(K)"结构测试）。K=100000 时
   `robust_beta` 的 O(K) 求和与 CDF 建表都会变慢，没有实测数据。
4. **`inconsistent` 计数器仍未在任何输入上观察到非 0**。我原本以为它
   能抓住第 5b 节那个篡改问题 —— 它抓不住，因为那条路径需要"两个独立
   来源比对"，而度 1 符号没有第二个来源。这个计数器的实际触发条件
   我没有构造出来（也许极难达到，也许它的设计假设错了）。
   **这是一个待查的悬空设计**，不是"已覆盖"。
5. **符号长度只测到 40 字节**。大符号（几 KB）的 XOR 热路径性能没有测。
6. **`payload_hash` 的碰撞行为没有实测**。FNV-1a 64 在"意外损坏"这个
   量级够用，但没有跑过 y 大量随机篡改统计漏检率。README 明确声明它
   不抗主动构造，这个声明本身没有实验支撑（它是关于算法性质的判断，
   不是实测结论）。

## 13. 与 `bitnum` 的关系

没有关系。`bitnum` 做的是数值格式编解码（整数/浮点的位级表示），
本项目是无速率纠删码（GF(256) 域运算 + 概率分布 + 剥皮）。

唯一的交集是"位运算要小心"，但连这点也不是同一个问题：这里的位运算
服务于 `xtime()`（域乘法）和 xorshift（PRNG），不是 IEEE 754 的字段拆分。
